Python library · stage runner

Process a batch of same-shaped directories, one stage at a time

Similar objects become directories, then move along a directed acyclic graph one stage at a time. An operator describes the transform. Where this run writes is decided by the run.

What is docorder

Progress lives in each object's own directory. A stage waits for the previous stage, then fills in what is unfinished and redoes what the upstream changed.

1 A batch of same-shaped objects

Tables or models pass through the same steps: take a source file, render a prompt, call a model, keep the result.

2 Calls are slow, and they stop halfway

A token limit, a process exit, or a non-zero command can happen after thousands of objects are already done.

3 Operators outlive one run

An operator describes a transform, not this run's output path. The output directory and any overrides are filled in when the job is assembled.

Core concepts

If docorder is new to you, get familiar with these few concepts first:

  • EntityOne directory holding a body and a tag. It is the smallest unit docorder processes.
  • Upstream snapshotRecords which upstream this result was computed from, and whether it has to be redone.
  • Operator and operator homeDescribes what one step does. It is independent of any single run and can be reused.
  • Epoch and stageThe name of one batch of results, and the unit of one stage of work.
  • Runner and expected namesWorks out which results this step should have, then compares them with the ones on disk.

Chapter 2, Core concepts and terms, defines all of them. For a quick lookup, see the glossary.

Model

An entity is one directory, an operator has one of five types, and a job is a graph. Where those three boundaries fall decides how a run lands on disk and how it resumes.

An entity is one directory

The directory name is the entity name. It cannot contain a slash, and it cannot start with . or _. data is the body, and tag.json holds traits for filtering and templates, plus the upstream snapshot when the entity has one. The start of the graph has no upstream, so it does not write that key.

20261015 is the epoch of this run, the subdirectory that holds the entities. A different epoch is a different subdirectory. The previous result stays where it is.

runs/
├─ tables/                 source
│  └─ 20261015/orders/
│     ├─ data             body
│     └─ tag.json         traits
└─ prompt/                 map
   └─ 20261015/orders/
      ├─ data
      └─ tag.json         includes upstream

An operator has one of five types

An operator's static files live in a home found through DOCORDER_HOMES. A home earlier in the list wins. type and class in props.json are required, and a job cannot change them. class is module:Class, or primary:Class to load primary.py in the home.

The functions that can be configured directly cover source, map, reduce, and apply. Fanout has a base class only; implement it in a home when you need it. parallelism and retry may also be written in the home, and adding a node can override them.

A job is a graph

Each node has a name, an operator home, and an output path for this run. The output path is not stored in the home. Every node other than a source declares one upstream. The runner executes in topological order. A node finishes completely before its downstream starts. Declaration order decides which of two independent nodes runs first.

runs/tables/20261015/… runs/prompt/20261015/…

A relative directory is resolved against the operator home. Each direct child directory that holds data and tag.json becomes one entity. The directory name is the entity name, and the body is the original text of data. A source rewrites from the directory only when start_from_scratch=True. Otherwise downstream reads the entities already at the output path. config may override same-named function parameters from the home. When parallelism is greater than 1 the runner slices the work across threads in the current process and does not start worker processes.

Running the same epoch again

The runner compares the expected names with the directories on disk. A model call retries inside the stage according to retry. After retries are exhausted, entities that already have a snapshot stay, and the next run continues from the rest.

orders
  • data
  • tag.json
  • upstream still matches
Stays

The recorded upstream hash and epoch both match the current upstream.

items
  • data
  • tag.json
  • no snapshot, or the hash changed
Run and overwrite

Expected, but not finished yet, or the upstream body has changed.

draft
  • data
  • tag.json
  • no longer on the list
Deleted

Still on disk, and no longer in the expected names.
