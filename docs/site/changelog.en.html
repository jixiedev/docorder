Changelog

中文

This file follows Keep a Changelog. Version numbers follow Semantic Versioning.

[Unreleased]

  • The guide gains two chapters. Chapter 4, "Fingerprints and hashes", works out what each of docorder's three kinds of hash covers and where each one is kept: the hash inside the upstream snapshot, fingerprint.depend, and fingerprint.record. It explains the split of work between depend and record and the moment each one is rendered, the placeholders a path template may use, the rule that a node config replaces the whole fingerprint rather than adding to it, and a step-by-step way to trace an entity that is redone on every run. Chapter 11, "A data governance case study", puts those mechanisms together with the real jobs under examples/data-governance/: four jobs in sequence, from the metric list of a dbt model to the root catalogue, the assignment table and the member tables, with a fanout that splits the result into fourteen root entities on the way. The existing chapters move down by one and best practices becomes chapter 12; the chapter numbers in the README, the glossary, the contributing guide, the documentation home page and the table of contents are updated to match.
  • The documentation site build clears docs/site/ first. Renaming a chapter no longer leaves an orphan page behind.
  • The guide gains eight inline SVG diagrams for the parts that prose alone cannot carry: how the concepts are layered, what one stage does, how an entity is judged on a re-run, what a run leaves on disk, how the five operator types map input entities to output entities, how the built-in template variables are grouped, how the two kinds of hash make one decision, and how the four jobs of the data governance case hand their results to each other. A new scripts/build_figures.py generates them, and the source of each diagram lives in docs/guide.md and docs/guide.en.md, so the diagrams show up both on GitHub and in the documentation site, which carries them over unchanged. The colours follow the warm paper and deep teal of the documentation site itself, and each figure comes with its own wording in both languages. The site gains styles for the diagrams: each one sits in a bordered card and its caption carries a "Figure N" badge; on a narrow screen a diagram scrolls sideways inside its card instead of shrinking into illegibility.
  • The documents are compiled into a static documentation site. A new scripts/build_docs.py turns the Markdown in this repository into pages under docs/site/: the guide is split by its second-level headings into one page per chapter, plus a table of contents for the guide, and one page each for the quick start, the glossary, the code of conduct, contributing, security, and the changelog, in both languages. The body of the home page is a hand-written fragment under scripts/templates/, and the script wraps it in the same page shell as the other pages. The generated pages no longer link to raw Markdown files, and the cross references in the text are rewritten to point at pages.
  • The documentation site is reorganised like the Apache Hudi documentation site. docs/index.html and docs/index.en.html change from an introduction page into a documentation home page: below the top bar there are three columns, a grouped sidebar on the left, the body, and an "On this page" table of contents on the right, and the body carries a breadcrumb and previous/next navigation. Every chapter of the guide is reachable from the sidebar through an anchor link, and the "Documentation" section lists all of them as cards. On a narrow screen the sidebar collapses into an expandable menu and the body comes first.
  • The documents are merged into one manual. The content of docs/design.md and docs/functions.md moves into docs/guide.md, and both files are removed. The English versions merge the same way into docs/guide.en.md, and docs/design.en.md and docs/functions.en.md are removed. The links in the README, the contributing guide, the glossary, and the introduction page are updated to match.
  • The documentation home page is reorganized. Section headings and the navigation now match one for one, the "Model" section is split into entities, operator types, and the job graph, a diagram of the job graph is added, and the terminology table is corrected (an operator has five types). The inline styles are gone, the folder metaphor is the same everywhere, and a heading no longer breaks across lines on a narrow screen.

  • The guide gains a chapter 10, "Best practices". It covers directory and naming conventions, incremental runs and idempotence, how to organise operator homes, error handling, the cost of calling a model, recovering from a failed run, and a table of common anti-patterns.

  • The documents are checked against the current code again. The README now documents the docorder status command and the full dependency list, and make quality and CI now run the example job under examples/data-governance/documentation/. The guide adds sections for the three built-in functions FileHashSource, EntityTemplateToLLM, and TemplateToLLM, completes the table of built-in functions, and rewrites the input data of chapter 9 as entity subdirectories. The function document moves Output out of the map chapter into its own apply chapter. The documentation home page adds the apply operator and docorder status.

  • Output accepts filename, a fixed file name. Override rename when the name depends on the entity.
  • Add EntityTemplateToLLM, a map. It renders one Jinja prompt per upstream entity and sends that to the LLM. The template sees one source path and tag, plus staging(name). header and tag_template mean the same as they do for TemplateToLLM.
  • Add TemplateToLLM, a reduce. It renders the whole upstream list into one Jinja prompt and sends that to the LLM. header keeps a CSV from the reply, and tag_template renders the entity tag. The template carries paths: source.path is an upstream data file, and staging(name) is the path of one file that already exists in .staging.
  • Add fingerprint. record stores file sha256 values on the entity tag after the entity is written and does not redo that operator. depend is compared before the run and a mismatch redoes the entity. A source records only record. An apply cannot declare a fingerprint. FileHashSource writes absolute paths into the tag and keeps the input body.
  • Remove the .docorder-output marker. A stage creates the node output directory and no longer refuses a non-empty directory. docorder status treats child directories whose names do not start with . as stages.
  • Output stays an apply function. There is no output operator. The default directory is .staging under the job root. rename chooses the file name, returns the entity name by default, and subclasses override it. name_template is gone.
  • Replace the output operator with apply. An apply node calls apply on each upstream entity, then calls finish. Neither method may return a value. It writes no entities and cannot have a downstream node. Publishing files is now the apply function Output.
  • tag.json no longer records current. A downstream snapshot is taken from the live upstream body and user tag. Editing an already written entity's data or tag.json redos dependents on the next run.
  • PromptToLLM keeps a data file the tool wrote into the target entity. After checking that it is non-empty UTF-8 text, only tag.json is written. Without that file, the body is still standard output.
  • The upstream snapshot now lives in tag.json as upstream. upstream.json is no longer written, and a leftover file is deleted on persist.
  • Each stage prints a progress bar on stderr, titled with the operator name. Map, fanout, reduce, and apply know the count for this run; a source advances as emit yields.
  • DirectorySource reads child directories that already look like entities: the directory name is the entity name, the body comes from data, and the tag comes from tag.json. Loose files and incomplete directories are skipped.
  • Output writes each upstream body as a file under .staging at the job root. The file name defaults to the entity name; a subclass overrides rename. directory selects another destination; a relative path is resolved from the operator home.
  • LLMTool moves to docorder.utils.llm_tool.
  • Artifact and Environment move to docorder.core.
  • Built-in functions move to docorder.functions.impl. Base classes are renamed to source_function, map_function, reduce_function, fanout_function, and rendered_map. Write the new module path in props.json class.
  • Environment now has only operator_props (function parameters) and template_env (operator / job / entity for templates). config, bind, namespace, bindings, and format_named are gone.
  • Map and fanout parallelism now uses a thread pool instead of a process pool. The slice threads share the operator, so parameters need not be picklable, and the starting script no longer needs if __name__ == "__main__": for this.
  • OperatorNode applies the node's config onto props at construction and then drops config; the public object is props. Operator.of then lifts the node's public fields onto the operator; after that the runner, the function, and the template environment read the operator, not the node. Function holds an environment: environment.operator_props is the function parameters and environment.template_env is the template view with operator, job, and entity, both built from the operator. Contract tests cover it.
  • Add the user guide docs/guide.md: background, core concepts, workflow, use cases, configuration, built-in functions by operator type, template variables of rendering functions and how to add more, writing your own function, a complete example of using docorder in your own project, and best practices. The English version is docs/guide.en.md.
  • The documents are checked against the current code and rewritten. The README now installs from the repository with uv sync, and adds getting the code, prerequisites, a runnable quick start and rerun example, configuration, and troubleshooting. The guide corrects the behaviour for duplicate node names, a reduce with an empty upstream, stage-wide clearing, parallel failures, and a failing source emit, and adds a rerun decision table, the fingerprint rules, a failure and retry comparison, and an end-to-end example. SECURITY.md and the documentation home page drop the cursor preset, which does not exist.
  • Chapters 2 and 3 of the guide are rewritten around the current stage scheduler: the state of entities, operators, and jobs, the epoch directory, and how one run compares upstreams and writes them.
  • Documents are provided in Chinese and English. Chinese keeps the original file name. English uses the same name with an .en suffix. The README is rewritten around the current Job and execute.
  • The documentation home page is docs/index.html.
  • Function documentation is collected in chapter 6 of the guide. Each function is one module under src/docorder/functions/.
  • A source operator accepts only a function. The function yields each entity's data and tag from emit. DirectorySource produces entities from a directory of existing entity subdirectories (data and tag.json). FilteredDirectorySource selects them by name endings and data size in filter.
  • The package no longer ships operator homes. Homes come from DOCORDER_HOMES. Concrete operators are implemented later.
  • execute receives the epoch. One run walks the whole graph in topological order.
  • Operator props.json uses type: source, map, reduce, fanout.
  • Entities are stored in an epoch subdirectory. The upstream operator, entity name, epoch, and hash are written to upstream.json in the entity directory. Another run of the same epoch executes what is missing, deletes what is extra, and redoes what the upstream changed.
  • The project name is docorder. The package, the command-line tool, and DOCORDER_DG, DOCORDER_LLM, and DOCORDER_HOMES all use that name.
  • Reusable operator implementations live in src/docorder/operators/. Stage scheduling lives in src/docorder/runner.py.
  • The data-governance example jobs became scripts under examples/data-governance/ (documentation, dbt_model, and semantic_layer), and are no longer installed through docorder run.
  • The llm and llm_batch operators are gone. A model is now called by the PromptToLLM, EntityTemplateToLLM, and TemplateToLLM functions. A tool preset is a JSON file in the operator home, and a command JSON can be passed in as well.
