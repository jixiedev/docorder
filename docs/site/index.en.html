Docorder / Docs / Overview

Python library · stage runner

Run the same transforms over a batch of directories, stage by stage

Run one set of steps over a batch of similar objects, such as table definitions, notes, or configs: render, then call an external tool or a model, and keep each result on disk with the object. After a stop or a change in the input, the same epoch continues and only redoes what is missing or stale.

What it does

Turn a multi-step batch over similar objects into a job that can stop and continue. The problem is set out in chapter 1.

A typical input is the definitions of hundreds of tables, a batch of notes, or a set of service configs. Every object goes through the same steps: render a prompt, hand it to a model, then collect the answers into one list. Some of those steps are slow, expensive, or prone to failure. An external command times out, a model API rate-limits, a template has a mistake. The input also keeps changing: one table definition today, a few new tables tomorrow.

A plain loop usually has to start over after a failure partway through, and the time and the model calls already spent are wasted. Keeping your own record of what finished is its own problem: a database is another component to run, and a record in memory disappears when the process exits. After one input changes, a script also has no basis for deciding which downstream results are still valid, so it recomputes everything, or a person decides by hand.

Docorder writes each object's result at each step as a directory on disk, and records in that directory a hash of the upstream content the step read. The next run of the same epoch compares those hashes: it fills in what never finished, redoes what the upstream changed, keeps what still matches, and deletes what is left over. The decision uses only the files. It needs no database, and it does not depend on anything the previous process left in memory. One stage finishes the whole batch before the next stage starts.

1 Entities on disk

Each directory holds a data body and a tag.json. The result of this step, and the upstream it read, stay with the object.

2 Operators in a graph

Five types: source, map, reduce, fanout, apply. Reusable transforms live under DOCORDER_HOMES; the job picks where this run writes.

3 Resume by epoch

The same name continues in the directories already there. A new epoch starts from empty directories and leaves the old batch in place. Details in How a run works.

Where it fits

A batch of independent objects, the same steps for each, and at least one step that is slow, expensive, or prone to failure. The job graphs are in chapter 5.

Generate prompts, then call a model

A source reads a batch of entity directories, a map fills a template for each object, and the next map hands each prompt to a command-line model tool. A reduce can then collect every answer into one list. Give the model node a retry for the occasional API error, and a parallelism to cap how many requests are in flight. After a fix, the same epoch redoes only the objects that never got an answer; the ones that already succeeded are not sent to the model again. The example in chapter 10 has this shape.

Generate config from structured data

The upstream body is JSON, for example the fields of a table or the description of a service. A template fills those keys into a jsonnet program, and the local jsonnet program compiles it into config or text of one format. This suits producing one family of config files from a batch of tables or services.

Run a command for each object

Command starts an external command once per entity. The arguments can refer to the body, the tag, and the output directory. The result is what the command prints, or a file it writes. The command is not run through a shell, so spaces in the arguments are not interpreted again. This suits formatters, converters, and scripts of your own team, called in bulk.

Gather, or split

A reduce folds the whole batch into one entity: an index, a table of contents, or a report. A fanout splits one entity into many, for example cutting a long document into chapters and handling each one afterwards. Fanout has no built-in function; you write it as chapter 9 describes, usually in a dozen lines.

The data governance jobs in the repo

examples/data-governance/ has three runnable jobs: write descriptions for tables, generate dbt models from table docs, and build a root catalogue from a metric list and assign each model a root. The catalogue work is four jobs in sequence, and each job's output is the next job's input. When a table or a model changes, a later run redoes only the affected part.

Where it does not fit

Shapes this version cannot express. See chapter 5 and the boundaries of this version.

  • Two upstreams at onceA node has one upstream. If a function reads a second result from disk itself, a change on that path does not redo the entity.
  • Several machines, or a pipelineParallelism is a thread pool on one machine. The upstream finishes the whole batch before the downstream starts. One finished entity is not handed on immediately.
  • Binary bodiesImages and audio do not fit. An entity body is text.
  • Few objects, fast stepsWhen starting over after a failure costs nothing, an ordinary Python script is the simpler tool.

Core terms

Enough to read the rest of the docs. Full definitions: chapter 2 and the glossary.

  • EntityOne directory: body + tag; the unit of work.
  • OperatorA reusable transform (home + props.json), not tied to one run’s path.
  • Epoch / stageOne named batch of results; one hop in the job graph.
  • Upstream snapshotWhat upstream this result came from—used to decide keep vs redo.

Getting started

Install from the repo, then follow the quick start. A fuller walkthrough is in chapter 10.

git clone https://github.com/jixiedev/docorder.git && cd docorder && uv sync

Python 3.10+ uv Operator homes via DOCORDER_HOMES
tables → prompt → answers

Build a Job, add operator nodes, call execute(job, epoch). Configuration reference: chapter 6.
